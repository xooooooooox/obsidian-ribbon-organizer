# Architecture

Ribbon and Status Bar Organizer ships three features, all configured from one settings panel:

1. **Ribbon groups**: orders ribbon icons into named groups separated by thin divider lines — the desktop left ribbon and the tablet drawer ribbon via flex `order`, the phone navbar ribbon menu (the ≡ button) via an intercepted menu rebuild — and hides/shows icons via an eye toggle that mirrors Obsidian's native hide and the Commander plugin's hide list.
2. **Quick menus**: a ribbon-menu launcher for user-picked commands with editable labels and icons (including iconize custom packs).
3. **Status bar**: reorders, hides (class-rule based), and restyles status bar items — three display modes, `{name}`-template rewrite rules with optional per-rule icon and per-part colors, device-local learned samples, a clone-based preview strip, and an optional floating pill on phones/tablets (default off).

## Overview — three layers

- **`src/core/`** — pure functions, no `obsidian` import. All grouping arithmetic and menu-entry shaping lives here; this is the only layer with unit tests.
- **`src/ui/`** — the settings panel and fuzzy pickers. Thin: every state change delegates to a core function, saves, and re-renders its own container.
- **`src/main.ts`** — the plugin shell, and the primary owner of non-public API (`app.workspace.leftRibbon`, `app.commands`, `app.statusBar`, `app.mobileNavbar`, and the Commander instance under `app.plugins`). The only other touchpoints live in `src/ui/`: `iconRender.ts`'s iconize accessor and the `app.plugins.manifests` reads in `StatusBarSection.ts` (row names) and `QuickMenusSection.ts` (entry-row plugin names). Private shapes are runtime-validated, never trusted.

## Module map (`src/`)

- **`main.ts`** — lifecycle and the two feature drivers.
  - Settings: `{ menus, groups, moreTucked, moreIcon, statusBarOrder, statusBarHidden, statusBarShowOnMobile, statusBarModes, statusBarRules }` (see Data model); `loadSettings()` normalizes every field (`normalizeMenus` — which also migrates the pre-0.4.0 flat `quickCommands` list — `normalizeGroups`, `normalizeMoreTucked`/`normalizeMoreIcon` plus a `pruneTucked(groups, moreTucked)` pass so a claimed id can never load already tucked, and the four statusBar normalizers), so a hand-edited `data.json` can never crash the plugin. This shape has no ribbon HIDE field: hide state lives in Obsidian's native `leftRibbon` items and in the Commander plugin's own settings, never in Ribbon and Status Bar Organizer's `data.json` — tuck membership is a separate axis and DOES live here (`moreTucked`; tucked ≠ hidden).
  - `ribbonInternals(app)` validates `app.workspace.leftRibbon` (`items[]` with `id`/`buttonEl`, plus `ribbonItemsEl`); returns null on any shape mismatch. An entry without `buttonEl` is NOT a mismatch — Obsidian's `removeRibbonAction` (plugin unload) deletes `buttonEl` but keeps the entry for its hidden/order state — so it is surfaced as `buttonEl: null`: `applyGrouping` counts it as hidden (no order write, no divider slot), `ribbonSnapshot` skips it, and `groupRibbonMenu`'s index alignment keeps it (Obsidian's phone menu builds a row for every non-hidden entry, mounted or not).
  - `cmdrAccess(app)` validates the Commander plugin (id `cmdr`) the same way, returning a three-state result — `absent` (not installed/enabled), `ok` (settings shape as expected, carries the plugin handle), `broken` (present but its `settings.hide` shape changed) — so every Commander touchpoint can branch on all three instead of assuming presence.
  - `rebuildCmdrStyle(hide)` replaces Commander's injected `<style id="cmdr">` the same way Commander itself does (remove, then re-append only when non-empty) using `commanderHide.ts`'s `cmdrHideStyleText`; needed because Commander's own stylesheet builder is module-private, so a same-session unhide would otherwise stay masked behind the stale rule.
  - `cmdrHiddenTitles()` reads the titles Commander currently hides (empty set when `cmdrAccess` isn't `ok`); combined with each item's native `hidden` flag this is the EFFECTIVE hidden state (native ∨ Commander) fed to both `ribbonSnapshot()` and `applyGrouping()`'s `computeRibbonLayout` call — the latter fix means a group whose members are hidden only via Commander no longer renders a phantom divider next to it. `applyGrouping()` also mirrors this per-item Commander state onto the button element itself, class `ribbon-organizer-cmdr-hidden` (styles.css `display: none !important; content-visibility: hidden`) — Commander's own hide CSS is title-keyed (`div.side-dock-ribbon-action[aria-label="<title>"]`) and misses an icon whose plugin temporarily rewrites its aria-label (remotely-save while syncing), which an element-anchored class can't be pierced by. Accepted staleness: the class updates on every `applyGrouping` pass, so an unhide done inside Commander's own settings UI only rebuilds Commander's stylesheet and never touches this element — the class lingers until the next ribbon rebuild (any ribbon churn or a restart) clears it; hides in either UI, and unhides through this plugin's own toggle (`setIconHidden`, which re-runs `applyGrouping`), stay immediate.
  - `setIconHidden(itemId, hidden)` is the single entry point the settings UI calls to toggle a row: it mutates the raw `leftRibbon.items[].hidden` flag, calls `leftRibbon.onChange(true)` (native persistence; also rebuilds the ribbon's DOM children, which drops injected dividers — hence the `applyGrouping()` call right after), then edits Commander's `hide.leftRibbon` title list via `withTitle`, saves Commander's settings, and rebuilds its stylesheet. Commander absent → native-only, silent; Commander present but shape-broken → native-only plus one Notice.
  - `applyGrouping()` writes flex `order` onto each icon's `buttonEl` and injects `.ribbon-organizer-divider` divs per `computeRibbonLayout`; idempotent; guarded by a session latch (`groupingDisabled`) set when internals validation fails (console.error + one Notice). Runs on desktop and tablet — both expose the same `.side-dock-actions` flex list — but not on phones, where the ribbon lives inside a rebuilt navbar menu rather than a flex list. Tucked ids (`settings.moreTucked` restricted to live, unclaimed ids) get class `ribbon-organizer-tucked` on their `buttonEl` (same display-none effect as the Commander class above, separate name — different owner, different lifecycle). When any tucked, non-hidden sentinel member exists, an RO-owned more button is rebuilt every pass like the dividers — never a registered ribbon item, so it can't recurse into this plugin's own settings — `div.side-dock-ribbon-action.ribbon-organizer-more`, `aria-label: "More"`, icon = `settings.moreIcon` via `renderIcon`, flex order = `layout.moreOrder`; its click opens a DOM `Menu` at the button's rect with one row per tucked, non-hidden live item (icon + title, both via `renderIcon`), `onClick` firing `item.buttonEl.click()` (a display-hidden element still dispatches clicks). `onunload` sweeps the button element and both element-anchored classes (`ribbon-organizer-cmdr-hidden`, `ribbon-organizer-tucked`) off every item.
  - Conflict standdown: before writing anything, `applyGrouping()` asks `ribbonArrangerConflict()` whether a plugin from `RIBBON_ARRANGER_PLUGINS` (core/ribbonConflict.ts) is enabled — those plugins move the ribbon's icon elements into their own wrappers, and their re-apply watcher and this one trigger each other synchronously until the app freezes (issue #1). On a hit grouping restores the stock ribbon via `restoreRibbon()`, notices once per session, and goes read-only — the observer stays attached so grouping resumes by itself once the arranger is disabled. NOT a session latch, unlike `groupingDisabled`, and deliberately not user-overridable: the list only carries plugins that provably rearrange the ribbon whenever enabled, so a "keep grouping on anyway" override could never end in real coexistence — only in the burst breaker tripping.
  - `observeRibbon()` — a MutationObserver (childList + subtree + `class` attribute) re-applies when icons appear late (lazy-loading plugins) or native hide/unhide toggles; it runs synchronously with no debounce, since callbacks fire at the microtask checkpoint before the browser paints, so the restore is invisible — a debounce was the flicker users saw. It is disconnected while `applyGrouping` writes (so our own edits can't re-trigger it) and on unload. Its callback also runs the burst breaker (`pushReapplySample`): more than `REAPPLY_BURST_LIMIT` foreign triggers inside `REAPPLY_BURST_WINDOW_MS` means an arranger NOT on the known list is looping with grouping — `tripGroupingBreaker()` then latches `groupingDisabled`, restores the stock ribbon, and notices. Triggers are not counted during a conflict standdown, where grouping is read-only and cannot be part of any loop.
  - `onunload()` clears every inline `order` and removes every injected divider — the stock ribbon returns instantly. The shared restore (`restoreRibbon()`) sweeps dividers and the more button subtree-wide, not direct-children-only: a coexisting arranger may have adopted them into its own wrappers.
  - `observeMenus()` — the phone counterpart of grouping, mobile-only (`Platform.isMobile`). The navbar ≡ button rebuilds a standard `Menu` from `leftRibbon.items` on every open (array order, skipping natively hidden items) and appends it directly to `document.body`; flex `order` does not apply to it. Property-wrapping `mobileNavbar.showRibbonMenu` cannot catch this open — the navbar's click listener captures a bound reference to the method at construction, so replacing the property afterwards never runs the wrap on a real tap — so a `MutationObserver` on `document.body` (childList only) watches for inserted `.menu` elements instead. `isRibbonMenuTrigger()` confirms an insertion is the ribbon menu (not some other menu) by checking `has-active-menu` on `mobileNavbar.ribbonMenuItemEl`, the class `Menu.showAtPosition` adds to its parent element before appending. The observer callback fires at the microtask checkpoint, pre-paint, so `groupRibbonMenu()`'s reorder is invisible; it only mutates nodes inside the menu element, never `body`'s child list, so it cannot retrigger itself. Disconnected on unload.
  - `groupRibbonMenu(menuEl)` maps the open menu's `.menu-item` rows to live ribbon items by index alignment (one row per native-visible item, in `items` order); on any mismatch it leaves the menu untouched — native order, degraded but correct, the safety valve for the moment Obsidian changes the menu shape. Commander's CSS hide targets `.side-dock-ribbon-action` elements and misses these menu rows, so Commander-hidden titles are removed here explicitly. The remaining rows are walked per `computeMenuRows(groups, effective)` — a DOM move per row (preserves its tap handler) plus a `div.menu-separator` between adjacent non-empty groups — and each quick-menu row's icon is re-rendered through `renderIcon` (the native menu only resolves registered icon ids). Every exit — grouped, bailed with row/visible counts, or no internals — records a `lastMenuOutcome` string that the diagnostics command below reads back.
  - `syncRibbonMenus()` rebuilds the plugin's composite ribbon icons from `settings.menus` (full remove-and-re-register; grouping's flex `order` keeps positions stable). `openMenu(evt, menuId)` builds that menu's dropdown from `quickMenuEntries`; `menu.setUseNativeMenu(false)` forces a DOM menu because native macOS menus cannot render command/iconize icons.
  - `ribbonSnapshot()` is the settings UI's read-only view of the live ribbon; its `hidden` field is the effective (native ∨ Commander) state described above, not the raw native flag.
  - `copyDiagnostics()` — the `copy-ribbon-diagnostics` command ("Copy ribbon diagnostics") copies a JSON snapshot to the clipboard: plugin version, platform flags, whether `mobileNavbar`/`ribbonMenuItemEl` are present, whether the menu observer is attached, per-item `{id, nativeHidden, cmdrHidden}`, and `lastMenuOutcome`. Exists because iOS has no console to inspect the phone-only mechanism above; a clipboard write failure surfaces as a Notice plus `console.error`, never silently.
- **`core/ribbonGroups.ts`** — the grouping model. `RibbonGroup` (`id`/`name`/`items`), the `UNGROUPED_ID` sentinel, `defaultGroups`, `normalizeGroups`, `computeRibbonLayout` (desktop/tablet flex order + divider orders, plus `moreOrder` — emitted right after the sentinel's members when at least one is non-hidden and `tucked`; `tucked` is honored only on sentinel members, ignored on claimed ones as a belt to `pruneTucked`'s suspenders), `computeMenuRows` (the phone counterpart: the same group walk, emitting an ordered `MenuRow[]` of visible item ids with a separator between adjacent non-empty groups; ignores `tucked` entirely — the navbar menu keeps flat-listing every icon), `normalizeMoreTucked` / `normalizeMoreIcon` (the `moreTucked`/`moreIcon` settings normalizers; `DEFAULT_MORE_ICON` = `"ellipsis"`), `pruneTucked(groups, moreTucked)` (drops ids a named group has claimed — a group claim always wins over a tuck), and the pure mutations `addGroup` / `renameGroup` / `deleteGroup` / `moveGroup` / `moveItemToGroup` — all return fresh arrays and throw on unknown ids or sentinel violations.
- **`core/ribbonConflict.ts`** — ribbon-fight protection, pure: `RIBBON_ARRANGER_PLUGINS` (the id/name list of plugins known to rearrange the ribbon DOM themselves; currently Open Ribbon Groups) and `pushReapplySample` with its `REAPPLY_BURST_WINDOW_MS`/`REAPPLY_BURST_LIMIT` thresholds — the sliding-window counter behind the burst breaker.
- **`core/statusBarItems.ts`** — status bar item identity (`key#index` from DOM class lists; a `plugin-<id>` class wins and makes every other class — state classes included — irrelevant; items without one key on their remaining non-generic classes), order computation (stored first, absent kept by the caller, new appended, pinned ids excluded), row sequence for the settings list, `normalizeStatusBarOrder`, cmdrHiddenSiblings (sibling migration when showing clears Commander's plugin-level hide), fallback display names. Pure.
- **`core/statusBarRules.ts`** — status bar text rewriting, pure: the `{name}` template engine (`applyStatusBarRules` — literal parts escaped, placeholders become lazy capture groups, anchored full-match, first active rule wins, malformed/empty templates never match; returns a `RuleResult` — `{text, icon, iconColor, textColor}`, the last three nullable — a rule needs find plus at least one target part (text or icon); `iconColor`/`textColor` are optional, independent per-part tints carried straight from the matched `StatusBarRule`), `autoTemplateRule` (chip click → longest shared prefix, else suffix, becomes the literal part and the remainder `{x}`; replace is bare `{x}`; one edge only), `pushSeen` (collapsed/deduped/capped LRU), and the three normalizers for `statusBarModes`/`statusBarRules`/`statusBarSeen`.
- **`core/commanderHide.ts`** — pure, Obsidian-free: replicates the Commander plugin's hide-stylesheet rule format (`cmdrHideStyleText`, byte-for-byte — leftRibbon rules by title, then statusbar rules by plugin id, preserved verbatim) and a list helper (`withTitle`, add/remove a title exactly once). Exists because Commander's own CSS builder is module-private, so Ribbon and Status Bar Organizer must be able to reproduce it to rebuild the stylesheet after editing Commander's hide list.
- **`core/quickCommands.ts`** — `quickMenuEntries()`: flags commands not registered on this device as `disabled` and normalizes separators (no leading/trailing/consecutive; a list with no runnable command collapses to `[]`). Also `commandOwnerId()`: a command id's prefix before the first colon — the owning plugin's id, or a core namespace like `editor`/`workspace`.
- **`core/quickMenus.ts`** — the quick-menus model: `defaultMenus`, `uniqueMenuName`, and `normalizeMenus` (validates persisted menus, fills missing ids, suffixes duplicate names, migrates the legacy flat `quickCommands` list).
- **`core/icons.ts`** — `iconChoices()`: composes Obsidian's built-in icon ids with iconize custom packs into one picker list (the `lucide-icons` pack is dropped — Obsidian already ships Lucide). Also `BRAND_ICON_ID` (`"ribbon-organizer"`) and `BRAND_ICON_SVG`, the plugin's brand mark; `main.ts` registers them via `addIcon` at load, so the id resolves like any built-in (appears in the icon picker without Iconize, renders through the ordinary ribbon/menu icon paths) and is the default icon `defaultMenus()` assigns to a new quick menu.
- **`core/types.ts`** — `QuickCommand` / `QuickSeparator` / `QuickEntry`, the `isSeparator` guard, and `QuickMenu` (one composite ribbon icon; ribbon id derives from `name`, `id` is the stable settings identity).
- **`ui/SettingTab.ts`** — the dual-path, three-tab panel (Ribbon / Quick menus / Status bar). `getSettingDefinitions()` (Obsidian 1.13+) returns one render-type definition whose name/desc/aliases feed settings search and whose row element hosts the whole tabbed panel; `display()` renders the same panel as the official < 1.13 fallback. Delegates the three tabs to their section classes; `hide()` tears down StatusBarSection's spotlight listeners, which live on the real status bar.
- **`ui/GroupsSection.ts`** — the Ribbon tab: a single column mirroring the ribbon's final order (group headers mark where dividers render), with in-place filter, collapsible groups (default collapsed; session-only `expanded` set, chevron + count pill on headers — plain member count, or `visible/total` with the total dimmed once ≥1 member is effectively hidden; a non-empty filter query temporarily reveals matches inside collapsed groups without touching the stored state — two distinct hidden classes, `is-filtered-out` vs `is-collapsed`), dual-path drag-and-drop — HTML5 from a mouse, the `ui/pointerDrag.ts` grip drag from touch, both resolving through one `hitAt` closure per drop target — (items within/across groups with half-zone insertion — a row's top half inserts before it, the bottom half after; an item dropped on a group header appends to that group with a whole-frame highlight, while a dragged group inserts before the header it lands on; dropping on a collapsed header appends without expanding), an eye `ExtraButtonComponent` per live item row (calls `plugin.setIconHidden`, then re-renders — hide state lives outside this plugin's own settings, so a save-and-`persist()` isn't enough), a ⋮ "Move to group" menu, and inline rename (click the group name; no separate edit button). One instance lives on the SettingTab so filter text and collapse state survive re-renders; `persist()` = save → `applyGrouping()` → re-render own container through `withScrollPreserved` (see `ui/scrollKeep.ts`). While a known ribbon-arranging plugin is enabled (`plugin.ribbonArrangerConflict()`), the tab opens with the standdown note (grouping is paused, disable one of the two, edits below still save); it disappears entirely when no arranger is around.
- **`ui/statusBarMode.ts`** — shared metadata for the three status-bar display modes (`full`/`compact`/`icon`): `MODE_NEXT` (cycle order), `MODE_ICON`, `MODE_NAME`. Consumed by both `StatusBarSection`'s cycle button and `StatusBarItemModal`'s pills so the two stay visually identical.
- **`ui/StatusBarSection.ts`** — the Status bar tab: (mobile-display toggle, clone-based preview strip with position: relative and inset: auto — the strip must be the containing block for plugin abspos children anchored outside the settings scroller, and `inset: auto` hardening resets any floating-status-bar offsets that load after plugin CSS without excluding the strip), three-way hover spotlight with tracked cleanup, per-item eye + display-mode cycle + rewrite wand, "Not shown right now" state, lock rows for self-positioned items, half-zone drag list — top half inserts before, bottom half after, append via the footer hint). Row display name: plugin manifest name, else the live element's `aria-label` (names Commander macros and other fallback-keyed items), else `fallbackItemName`. Row layout: on desktop the middle element (preview text, status note, or plugin chip) carries the right-pushing auto margin; on phones the preview and chip are hidden, so the button group carries it instead — notes follow the title, and missing rows (no buttons) keep their right-aligned note. Self-contained drop logic (per-target `hitAt` closures shared by the HTML5 and `ui/pointerDrag.ts` paths; pinned rows never wire a drag handle); GroupsSection's group semantics don't apply.
- **`ui/StatusBarItemModal.ts`** — the per-item customize modal: display-mode pills, the seen-state preview (each learned value shown with what the current rules make of it — icon and text tinted per the matched rule's `iconColor`/`textColor`; click a sample to start an auto-templated rule), and the rewrite-rule editor with a per-rule optional icon (IconSelectModal; icon or text or both — both empty is an inert draft) plus one color dot per part (`iconColor`, `textColor`; native `<input type=color>` behind a button — unset shows a dashed hollow dot, set shows a filled swatch with a hover × clear; the picker's opened value falls back to the other part's color, so matching both parts takes two clicks). On phones, seen rows stack (chip full width, arrow and result wrap to a second line via `body.is-phone` flex-wrap). On all mobile platforms, clear badges are always visible and sized for touch (not just on hover), and ringed against the swatch background; the transparent color input gains `pointer-events: auto` so iOS can open the system picker from a real tap (programmatic `.click()` is ignored). The two opening paths: desktop has the input visually hidden and uses programmatic clicks; mobile keeps it invisible but hit-testable, so the tap lands on the input itself. Every change saves and re-applies immediately; find/replace text edits refresh only the preview (keeping other rows' inputs alive), while icon pick/clear, color pick/clear, and row add/delete re-render the modal body.
- **`ui/QuickMenusSection.ts`** — the Quick menus tab: one collapsible section per menu (default collapsed; session-only `expanded` set; new menu starts expanded), header = chevron + icon button (icon picker) + click-to-rename name (in-place input; empty/duplicate names revert — names are the ribbon ids) + command count + delete; body = the per-entry rows (icon button, label input, the owning plugin's name with the command's registered name and exact id in the hover tooltip, trash; separators) with grip-handle drag-and-drop (HTML5 from a mouse, `ui/pointerDrag.ts` from touch) — drop on a row's top/bottom half inserts before/after it, drop on a menu header (whole-frame highlight) appends to that menu's end (own header included; collapsed headers accept drops) — and that menu's add bar. Menu-level changes call `plugin.syncRibbonMenus()`; entry-level changes (including drag moves) only save.
- **`ui/pointerDrag.ts`** — the touch half of every reorder: HTML5 drag-and-drop never fires from touch in the mobile WebView, so `createPointerDragList` gives each section a per-render drag registry. `wireHandle` starts a drag from a grip on any non-mouse pointer (pointer capture; the grip's CSS `touch-action: none` is what keeps the rows themselves scroll surfaces), `wireTarget` registers the same `hitAt` closure the target's HTML5 listeners resolve through, so each target's indicator choice and drop action exist once. Hovers hit-test via `document.elementFromPoint` (collapsed/filtered rows are `display: none` and never hit, preserving the append-on-collapsed-header semantics); the drop re-resolves at the release point; `pointercancel`/`lostpointercapture` clean up without dropping; the source row wears `ribbon-organizer-drag-source` (dimmed) in place of a native drag ghost. Edge auto-scroll while dragging is deliberately absent — it needs a rAF loop; long jumps work as multi-hop drags or via the ⋮ "Move to group" menu.
- **`ui/scrollKeep.ts`** — `withScrollPreserved(el, render)`: walks up from `el` to the nearest scrollable ancestor, records its `scrollTop`, runs `render()`, then restores it. `GroupsSection`/`QuickMenusSection` empty and rebuild their whole container on every state change; depending on browser reflow timing the nearest scrollable ancestor can clamp `scrollTop` to 0 while the container sits empty (seen on phones — the eye toggle snapped the settings list back to the top). Wrapping the re-render in this removes that timing dependency.
- **`ui/iconRender.ts`** — `renderIcon()` fallback chain: Obsidian `setIcon` → iconize `setIconForNode` → the command's own icon → `"command"`; plus the iconize public-API accessor. An iconize-injected svg is normalized in place — its fontSize-px `width`/`height` attributes and the extra-margin style iconize writes on the host node are stripped, `svg-icon` class added — so pack icons adopt the host surface's native metrics; without this a pack icon on the ribbon renders smaller and offset against its neighbours.
- **`ui/IconSelectModal.ts` / `ui/CommandSelectModal.ts`** — `FuzzySuggestModal` pickers over the icon catalog / command registry.

## Core invariants

1. **Grouping is visual-only.** Flex `order` + injected divider divs on `.side-dock-actions` (a flex column, so `order` fully controls visual sequence). `applyGrouping()` never touches Obsidian's items array, DOM node order, or drag persistence; unload or disable restores the stock ribbon. Hiding is the one deliberate exception: `setIconHidden()` writes the native `hidden` flag and Commander's hide list on purpose, as a separate, explicit call the settings UI makes — never as a side effect of grouping.
2. **Private API is validated, never trusted.** `ribbonInternals()` returning null means "internals changed shape" — grouping disables itself for the session with one Notice. No partial writes, no guessing.
3. **Match key = registration id** (`pluginId:title`, e.g. `config-sync:Config Sync`) — stable at runtime, unlike aria-labels which localize and change with state.
4. **Sentinel semantics.** Exactly one group with id `ungrouped` always exists in `settings.groups`; its `items` stays empty — membership is derived at layout time as "every live icon no other group claims". Its array position sets where unclaimed icons render. It cannot be renamed or deleted; `normalizeGroups` re-inserts it (at the end) when missing and repairs duplicates/malformed entries.
5. **Divider rule.** A divider renders only between ADJACENT NON-EMPTY groups, where non-empty means "has at least one live member that is not effectively hidden (native ∨ Commander)" — so hidden-only (by either layer) or absent-on-this-device groups never produce stray lines.
6. **Cross-device tolerance.** A configured item id absent from the live ribbon is skipped by layout and shown greyed ("Not on this device") in settings; it recovers automatically when its plugin returns. Same contract as quick-menu entries' `disabled` flag.
7. **Settings tab is dual-path** (see module map). `minAppVersion` stays 1.8.7 until the `display()` fallback is dropped.
8. **Platform split.** Quick menus run everywhere (`isDesktopOnly: false`). Grouping runs everywhere too, but through two different mechanisms depending on which ribbon surface the platform exposes: desktop and tablet share the flex-order path (`applyGrouping`, `computeRibbonLayout`) over the same `.side-dock-actions` list; phones don't expose that list — the ribbon lives inside a menu the navbar rebuilds on each open — so they go through the observed-menu path (`observeMenus`, `groupRibbonMenu`, `computeMenuRows`) instead.
9. **Status bar identity is derived from DOM classes** (`app.statusBar` has no item registry). Accepted limitation: a plugin creating several items in unstable order can swap its own items' slots; the escalation path (extra-class fingerprints) is documented in `docs/superpowers/specs/2026-07-28-statusbar-order-and-mobile-design.md`, not built.
10. **An untouched status bar config leaves a byte-for-byte native bar**: while `statusBarOrder`, `statusBarHidden`, `statusBarModes`, and `statusBarRules` are ALL empty and no write pass has run this session, the apply pass is a strict no-op and no observer attaches (`statusBarSeen` never counts — learning must not change rendering). Once any of the four has content, the pass writes inline `order` and compact-mode styles and toggles the hide/icon-only classes; when all four empty out again a session flag (`statusBarStylesApplied`) grants exactly one clearing pass that removes the residue (inline styles and classes) and detaches the observer. Unload clears everything.
11. **The mobile pill is pure CSS** in `styles.css`, gated on `body.ribbon-organizer-mobile-sb`; main.ts toggles that class only when `Platform.isMobile` and `statusBarShowOnMobile` are both true.
12. **Pinned status bar items are never ordered.** The apply pass probes each element (clear inline `order`, read computed, restore/write in one JS task — no paint in between); a non-zero computed `order` means the plugin positions the item itself (quick-explorer's `order:-9999` + `flex-grow:1` left-region spacer) and Ribbon and Status Bar Organizer leaves its position alone. Overriding it was the 0.9.x bar-split bug.
13. **Status bar hide is asymmetric two-layer.** Hiding writes only `statusBarHidden` (per-item); reading merges Commander's plugin-level `hide.statusbar`; showing clears both, migrating the plugin's other live items into `statusBarHidden` first. Own-layer hiding is a class rule (`ribbon-organizer-sb-hidden`, `display: none !important` in styles.css), never an inline `display`: item owners rewrite their own inline display on every leaf change, which silently erased an inline hide (the 0.14.1-and-earlier bug); the class survives those writes, and the apply pass clears any inline `display` left by pre-0.14.2 builds. Commander's stylesheet keeps handling its own rules.
14. **The preview strip is inert clones.** `cloneNode(true)` of visible items into a `status-bar ribbon-organizer-sb-strip` container (theme CSS matches, ids stripped, aria-hidden, no listeners copied); the mobile-pill CSS block excludes the strip via `:not(.ribbon-organizer-sb-strip)` on every selector.
15. **Rewriting is fail-open and text-node-scoped, with one structural exception plus one style-only touch.** Rules touch individual `Text` nodes; a matched rule with an icon additionally owns one `span.ribbon-organizer-sb-ricon` immediately before the node (re-rendered on id change, removed with the rewrite) — its own `iconColor` wins as an inline `color`, else an inline `color: var(--status-bar-text-color)` reset when the matched rule carries a `textColor` (so a text tint never bleeds into an uncolored icon), else no inline color at all. The second, style-only touch: the first rewritten node whose rule carries a `textColor` (first colored match wins) tints the whole host `.status-bar-item`, once per apply pass, via a memoized inline `color` (`syncHostTextColor`, `WeakMap<HTMLElement, {prior, written}>` — first tint records the pre-tint `style.color` as `prior`; the skip-guard for redundant writes is the `written` value the plugin last wrote, not a `style.color` read-back, because the CSSOM serializes a hex write into `rgb()` and would never string-match; a no-tint pass restores `prior` and clears the memo). Unmatched or malformed templates leave the plugin's text exactly as written. Loop safety: a `WeakMap<Text, {original, written, iconEl?}>` — a node whose data equals `written` is our own write and is skipped; unload and rule removal remove the span and memo entry unconditionally, restoring `original` only where `written` still stands (a host-overwritten node keeps its newer text; the rewrite pass sweeps such stale spans too) and clearing the host color memo via the same restore path (`restoreStatusBarText`). One MutationObserver per rule-bearing OR Compact-mode item (Compact needs churn tracking to keep the hover title = raw text), recreated when its element is rebuilt.
16. **Learning never renders.** `statusBarSeen` (cap 8 per item, LRU) samples raw pre-rewrite text at `statusBarSnapshot()`, the rewrite pass inside `applyStatusBarOrder()`, and every rule observer callback; it never makes the apply pass active, and only a genuinely new value schedules a debounced (2s) write to device-local storage via `app.saveLocalStorage` — never `data.json` — with `onunload` flushing synchronously if a debounced write is still pending.
17. **Grouping never fights another ribbon plugin.** The ribbon is shared territory: a plugin that moves the icon elements into its own wrappers re-triggers grouping's observer, and grouping's chrome re-triggers that plugin's watcher — a synchronous loop that freezes the app before it can paint (issue #1). Two defenses, both ending in the stock ribbon rather than a frozen one: a known-arranger standdown (`RIBBON_ARRANGER_PLUGINS`; recoverable within the session) and the observer's burst breaker (`pushReapplySample`; session latch, catches arrangers not on the list). The list's admission bar keeps an override switch unnecessary: only plugins that provably rearrange the ribbon whenever they are enabled. Both notice; neither touches quick menus or the status bar.
18. **Tucking is settings-owned and class-based, layered on top of grouping.** `moreTucked` lives in `data.json` (unlike hide state); `applyGrouping()` mirrors membership onto each item's `buttonEl` as class `ribbon-organizer-tucked` (`display: none !important`) and rebuilds the more button, but never reorders the ribbon DOM or touches Obsidian's items array — same guarantee as grouping itself (invariant 1); `onunload` clears the class and removes the button, restoring the stock ribbon. Hidden (native ∨ Commander) always wins over tucked: a hidden item is never listed in the more menu and never keeps the button alive, even when it is also tucked.

## Data model

`data.json` (rides whatever vault sync the user runs):

```json
{
  "menus": [
    {
      "id": "a41c…",
      "name": "Quick menu",
      "icon": "menu",
      "entries": [
        { "commandId": "remotely-save:start-sync", "label": "Sync now", "icon": "refresh-cw" },
        { "kind": "separator" }
      ]
    }
  ],
  "groups": [
    { "id": "b2f1…", "name": "Sync", "items": ["config-sync:Config Sync", "remotely-save:remotely-save"] },
    { "id": "ungrouped", "name": "Ungrouped", "items": [] }
  ],
  "moreTucked": ["zk-prefixer:Create new unique note"],
  "moreIcon": "ellipsis"
}
```

`normalizeGroups` makes this hand-editable: malformed entries and duplicate group ids are dropped, duplicate item claims deduplicate first-group-wins, the sentinel's name/items are forced.

- `moreTucked: string[]` — ribbon item ids tucked into the more menu; meaningful only for Ungrouped members (`pruneTucked` drops any id a named group claims, at load and on every groups mutation). Ids absent on this device stay in the array — same survival rule as `groups[].items` — and cannot summon the button, since layout membership derives from live icons only.
- `moreIcon: string` — icon id for the more button; `"ellipsis"` until customized.
- `statusBarOrder: string[]` — status bar item ids (`key#index`), left-to-right; ids absent on this device stay in the array so a reorder never evicts another device's items.
- `statusBarHidden: string[]` — item ids hidden by this plugin's own layer; Commander's plugin-level status bar hides merge in at read time only.
- `statusBarShowOnMobile: boolean` — default false; the "Show on phones and tablets" toggle.
- `statusBarModes: Record<id, "compact" | "icon">` — display mode per item; Full = no entry.
- `statusBarRules: Record<id, {find, replace, icon?, iconColor?, textColor?}[]>` — `{name}` template rewrite rules; `icon` is an optional icon id shown before (or instead of) the text, and `iconColor`/`textColor` independently tint each part when set; drafts with no target never match and are kept.

Learned status-bar samples are the one piece of plugin state that does NOT live in `data.json`: `statusBarSeen: Record<id, string[]>` (cap 8 per item, newest last) is device-local by definition ("seen on this device"), stored via `app.saveLocalStorage`/`loadLocalStorage` under the key `ribbon-organizer-status-bar-seen` — syncing it through `data.json` would churn on every relative-time status tick across every synced machine. `loadSettings()` runs a one-time migration: a pre-0.13 `statusBarSeen` field found in `data.json` is merged into local storage (entries already learned on this device win), the merged set is saved back to local storage, and the legacy field is dropped from `data.json` by a normal `saveSettings()` (the field no longer exists on `RibbonOrganizerSettings`).

## How to extend

- **A new grouping behavior**: add a pure function to `core/ribbonGroups.ts` with tests, then wire it from `GroupsSection` (state change → `persist()`). `computeRibbonLayout` is the single source of truth for what the ribbon looks like.
- **A new quick-entry kind**: extend the `QuickEntry` union in `core/types.ts`, teach `quickMenuEntries` its menu shape and `normalizeMenus` its persisted shape, and add its row renderer in `QuickMenusSection.renderEntries`.
- **When every target device runs Obsidian ≥ 1.13**: raise `minAppVersion`, delete `display()` in `ui/SettingTab.ts` and the matching `no-deprecated` scope-off in `eslint.config.mts`.
